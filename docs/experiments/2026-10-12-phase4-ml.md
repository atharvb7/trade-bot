# Phase 4: ML filter on 5-minute candidates (walk-forward)

Date: 2026-10-12 · Branch: `phase-4/ml` · Script: `scripts/train_model.py`
Data: 18,116 tradeable 5m candidates (decision 09:30–14:45), 2025-10-17 .. 2026-10-09.
Base win rate 38.2%; mean net R per candidate −1.02.

## Protocol
Rolling calendar-month folds: 6 months train · 1 month validation · 1 month test → 6 test
months (May–Oct 2026). LightGBM (fixed params in `config/settings.yaml`), Platt calibration
and the ML threshold are fit on the validation month only. If no threshold has positive mean
net R on validation (≥ 20 candidates), the fold does not trade. Everything below is test-month only.

## Sanity checks
- Shuffled labels (train + validation shuffled, 5 seeds): mean OOS AUC **0.507**, i.e. the real
  model is indistinguishable from the shuffled control.
- Pipeline health: features ≤ 0.4% NaN, none constant; in-sample AUC 0.86 vs 0.50 OOS (fits noise).
- Single-feature AUCs are all 0.50–0.53.

## Conclusion
The 25 features contain no out-of-sample information about whether these three setups hit
target before stop. An ML filter cannot rescue them. A Jev confirm/veto layer (Phase 5) would
see the same pre-computed numbers, so it is very unlikely to find an edge the model cannot,
and replaying ~18k states would cost API calls. Go-live targets are not met.
